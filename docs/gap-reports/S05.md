# S05 Permission Pipeline 差距报告

## 已理解并验证

S05 已把 S04 固定 Gate 提升为类型化 Policy Kernel：三种模式、声明性
`ALLOW/ASK/DENY`、不可由规则顺序改变的优先级、绑定可信 ToolSource 与 selector 的
Session Grant、Protected Paths/Hard Denial、Policy/Surface 异常的类型化 Fail Closed、唯一
最终 Permission Lifecycle、隐私安全事件摘要、Print Fail Closed 和重复拒绝防循环均已有
确定性测试。Fake MCP/Plugin/Sub-Agent 证明所有来源继续经过同一 Registry/Pipeline、审批、
事件和 64K 字符最终上限。

## 仍弱于成熟 Harness 的能力

- Startup Rules 只能由可信 Composition Root 编程注入，尚无 User/Project/Local/Managed
  Settings、规则文件、来源诊断或配置迁移；属于 S08/S13；
- Session Grant 与拒绝计数只在内存中，进程退出不恢复，也没有 Checkpoint、未完成副作用
  检测或 Undo；属于 S06；
- selector 已绑定可信 ToolSource，但真实 MCP/Plugin/Sub-Agent Adapter、命名空间、认证、
  Schema 变化、信任 UX 与传输故障尚未实现；属于 S10-S12；
- Lifecycle 只有内部观察语义，不能由外部 Hook 阻断、修改或扩展 Permission；属于 S09；
- Protected Paths 是应用层预拒绝，文件 Tool 仍依赖 WorkspaceGuard 在执行前复验 realpath；
  这不是 OS File/Process/Network Sandbox，攻击性隔离属于 S13；
- 当前拒绝阈值是固定的本项目产品决策，没有用户可配置治理、长期统计或模型分类；属于
  S14；
- stdio v0 和 TUI 的 `allow_session` 已可用，但协议仍是实验性内部协议，不具备 S14 的
  跨版本兼容承诺；
- S05 目前只有工作树 G3-G5 证据。只有在聚焦 Commit 上重新完成全量复验、文档对账和维护者
  code review 后，才能通过 G6 并把 Stage Exit 标记为 Accepted。
