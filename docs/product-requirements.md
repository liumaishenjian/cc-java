## 1. 文档目的

本文档定义 `cc-java` 的产品定位、目标用户、阶段范围、功能需求、非功能需求与验收标准。技术实现应以本文档为需求来源；如实现方案改变产品行为，应先更新本文档，再修改代码。

## 2. 产品背景

Java 团队已经普遍使用 AI 生成代码，但“能生成代码”不等于“能可靠地完成缺陷修复”。一个真实的 FixBug 流程通常还需要：

- 理解缺陷描述并识别缺失信息；
- 在受限范围内搜索代码、日志与数据证据；
- 形成可复核的根因判断；
- 在隔离工作区中修改代码；
- 执行编译和相关测试；
- 把补丁、验证结果、风险和未决问题交给开发者审核；
- 避免直接推送、合并或修改外部缺陷系统。

`cc-java` 希望用 Java 和 Spring AI 独立实现这条链路，并把安全边界、执行轨迹和可评测性作为一等能力，而不是做一个只会对话或只会生成代码的演示项目。

## 3. 产品定位

一句话定位：

> 面向 Java/Spring 仓库的安全型 Coding Agent，支持代码调查、受控修改、构建验证和人审 FixBug 工作流。

项目的第一个真实业务场景是自动化 FixBug，但底层能力应保持通用，使其以后可以支持代码解释、测试用例生成、变更审查和测试提效。

## 4. 产品目标

### 4.1 业务目标

- G-01：让开发者从“手工翻代码”转向审核结构化调查报告和补丁证据。
- G-02：将自动修复限制在隔离环境和明确授权范围内，不直接污染开发者工作区。
- G-03：让每次模型调用、工具调用、修改和验证都有可追踪结果。
- G-04：为后续接入缺陷系统、测试日志、测试数据库和 MCP 工具保留清晰扩展点。

### 4.2 学习与开源目标

- G-05：完整实践 Agent Loop、Tool Calling、上下文管理、权限控制、状态机、评测和可观测性。
- G-06：展示 Java/Spring 开发者如何构建工程化 Coding Agent，而非复制某个现有产品。
- G-07：形成可以公开演示、复现和评测的开源项目，作为个人技术作品。

## 5. 非目标

以下内容不属于首期目标：

- 完整复刻 Claude Code、Codex 或任意商业 Coding Agent；
- 使用或改写泄露源码、闭源实现或公司内部代码；
- 替代 IDE、代码托管平台或缺陷管理平台；
- 自动提交、推送、创建 PR、合并分支或评论缺陷单；
- 让模型执行任意 Shell 命令；
- 一开始就支持多 Agent、分布式任务、向量数据库或通用插件市场；
- 一开始就构建桌面端；
- 对“修复一定正确”作保证。

## 6. 目标用户

### 6.1 Java 后端开发者

希望快速理解陌生代码、定位缺陷，并获得带证据的修复建议或候选补丁。

### 6.2 技术负责人或补丁审核者

希望早上集中审核夜间生成的调查报告、Diff 和测试结果，而不是直接接收未经验证的代码。

### 6.3 测试工程师（后续阶段）

希望通过缺陷描述、日志和测试数据生成更完整的调查材料，并在提测前获得验证建议。

## 7. 核心使用场景

### UC-01：本地代码调查

开发者指定一个本地 Java 仓库和问题。Agent 仅使用只读工具搜索、读取并分析代码，最终输出带文件和行号证据的回答。

### UC-02：缺陷调查报告

Agent 接收结构化缺陷信息，检查描述是否完整，搜索相关代码与可用证据，输出可能根因、建议验证步骤、建议修改位置以及是否需要人工补充。

### UC-03：影子模式修复

Agent 在独立 Git Worktree 和独立分支中生成候选补丁，执行允许的编译与测试，输出 Diff 和证据报告。开发者决定接受、拒绝、补充信息或手工接管。

### UC-04：批量夜间调查（后续阶段）

外部调度器读取分配给团队的缺陷，逐个触发调查或影子修复。Agent 不自动写回缺陷系统，次日由开发者统一审核。

## 8. 阶段规划

| 阶段 | 名称 | 核心结果 | 明确不包含 |
| --- | --- | --- | --- |
| M0 | 文档与决策 | PRD、技术设计、协作规则、README 定版 | 业务代码 |
| M1 | 只读调查 Agent | 本地仓库问题 → 工具调查 → 带证据回答 | 写文件、执行构建、MCP、持久化会话 |
| M2 | 影子修复 Agent | Worktree → 候选补丁 → Maven 验证 → 人审报告 | 推送、合并、外部系统写入 |
| M3 | FixBug 工作流 | 缺陷摄取 → 信息检查 → 调查 → 修复 → 验证 → 人审 | 无人值守发布 |
| M4 | 工具生态 | MCP、项目指令、私有适配器 SPI、历史回放评测 | 默认开放所有外部工具 |
| M5 | 桌面端 | 会话、进度、审批、Diff 和证据可视化 | 替代 IDE |

M1 是第一个必须完成的垂直闭环。M2 开始才具备“自动修复”能力；M1 的价值是先证明 Agent 的判断过程可控、可测、可审计。

## 9. M1 功能需求：只读调查 Agent

### 9.1 会话与输入

- FR-001：用户可以通过 CLI 指定本地仓库路径和调查问题。
- FR-002：启动时必须校验仓库路径存在、可读，并确定唯一的真实根路径。
- FR-003：每次运行必须生成唯一 `runId`，并记录开始时间、结束状态和限制使用情况。
- FR-004：首版一次 CLI 调用只处理一个问题，不要求多轮交互或跨运行记忆。

### 9.2 Agent Loop

- FR-010：模型可以直接回答，也可以请求一个或多个已注册工具。
- FR-011：工具调用必须由应用执行，模型本身不能直接访问文件系统或进程。
- FR-012：每次运行必须限制最大模型轮次、最大工具调用数、总耗时和单次结果大小。
- FR-013：同一模型回合返回多个工具调用时，首版按返回顺序串行执行。
- FR-014：达到限制、模型异常、无效响应或用户取消时，必须以明确状态结束，不能无限循环。
- FR-015：未知工具、非法参数和可恢复的工具错误应形成结构化结果返回模型，并计入调用限制。

### 9.3 只读工具

- FR-020：`list_files` 可以列出工作区内文件，并支持数量和深度限制。
- FR-021：`read_file` 可以按行范围读取允许的文本文件。
- FR-022：`search_text` 可以在允许目录内搜索文本并返回文件、行号和片段。
- FR-023：`git_diff` 可以读取当前仓库变更，但不能调用外部 diff 或 textconv 程序。
- FR-024：所有路径型工具必须拒绝绝对路径、路径穿越、符号链接或 Junction 越界。
- FR-025：工具必须默认忽略 `.git`、`target`、`node_modules`、构建产物和已知敏感文件。
- FR-026：M1 不提供写文件、删除文件、任意命令、网络请求或外部系统工具。

### 9.4 输出与证据

- FR-030：最终回答应区分“事实证据”“推断”“未知信息”和“建议下一步”。
- FR-031：引用代码事实时，应尽可能包含相对文件路径和行号。
- FR-032：工具执行过程应产生事件，至少包含步骤、工具名、耗时、状态和截断标记。
- FR-033：默认不在日志中记录完整 Prompt、完整源码、工具参数、工具结果或 API Key。
- FR-034：M1 默认输出到终端；会话持久化和报告文件留到后续阶段。

## 10. M2 功能需求：影子修复 Agent

- FR-100：每个任务必须创建独立 Git Worktree 和独立分支。
- FR-101：不得直接修改用户当前工作区。
- FR-102：Agent 只能通过受控补丁工具修改 Worktree 内文件。
- FR-103：写操作和进程执行必须经过确定性的权限策略；交互模式下还需人工批准。
- FR-104：只允许执行预定义的 Git、Maven 和测试命令模板，模型不能提供完整命令行。
- FR-105：构建和测试必须有超时、输出上限、退出码和取消机制。
- FR-106：最终报告必须包含问题摘要、根因判断、修改文件、Diff、编译结果、测试结果、风险和未决问题。
- FR-107：默认禁止 commit、push、merge、创建 PR 和写回缺陷系统。
- FR-108：开发者可以选择接受补丁、拒绝补丁、要求重新调查、补充信息后继续或手工接管。

## 11. M3 功能需求：FixBug 工作流

- FR-200：通过适配器读取缺陷信息，并转换为与具体平台无关的 `BugCase`。
- FR-201：在调查前检查复现步骤、期望结果、实际结果、环境、时间范围和关联服务等信息。
- FR-202：信息不足时进入 `NEEDS_INPUT`，不能凭空开始修改。
- FR-203：支持按策略查询测试日志、只读测试数据库和关联代码；公司专用实现不得进入公开仓库。
- FR-204：采用显式状态机管理调查、修复、验证和人审，不依赖自然语言隐式决定流程状态。
- FR-205：外部调度与批处理由独立入口触发，单个 Agent Run 仍保持隔离。
- FR-206：所有外部系统写操作默认关闭，未来开放时必须单独授权并可审计。

## 12. 非功能需求

### 12.1 安全

- NFR-001：权限由确定性代码判断，仓库内容和模型输出不能改变安全策略。
- NFR-002：工作区外的文件访问必须被拒绝。
- NFR-003：API Key 只能来自环境变量或外部秘密存储，不进入仓库、Prompt 或普通日志。
- NFR-004：工具遵循最小权限和按请求暴露原则。
- NFR-005：远端写操作在 M1-M3 默认禁止。
- NFR-006：公开仓库不得包含公司域名、接口、日志、数据库结构、真实缺陷或业务源码。

### 12.2 可测试性

- NFR-010：核心 Agent Loop 不依赖真实模型即可进行离线单元测试。
- NFR-011：真实模型测试必须是显式启用的集成测试，不能成为普通 CI 的必要条件。
- NFR-012：安全规则、终止条件、消息顺序和工具轨迹必须有自动化测试。
- NFR-013：M1 运行前后仓库内容应保持不变，并可通过测试验证。

### 12.3 可移植性

- NFR-020：优先支持 Windows 11 和主流 Linux。
- NFR-021：路径、进程和换行处理不得假设只运行在 Unix。
- NFR-022：M1 的文件搜索应具备纯 Java 实现；外部搜索程序只作为后续可选加速器。

### 12.4 可观测性与隐私

- NFR-030：每个运行应能统计模型轮次、工具次数、耗时、Token 使用和结束原因。
- NFR-031：原始 Prompt、Completion 和工具内容默认不导出到可观测系统。
- NFR-032：审计事件与调试日志分离，前者只记录脱敏元数据。
- NFR-033：不得仅依赖分布式 Trace 重建 Agent 执行历史。

### 12.5 可维护性

- NFR-040：核心领域和 Agent Loop 不依赖 Spring AI 类型。
- NFR-041：模型提供方、工具和外部系统通过端口/适配器替换。
- NFR-042：先完成最小垂直闭环，再按真实需求拆分模块。

## 13. M1 验收标准

M1 只有同时满足以下条件才算完成：

1. 用户能对一个本地 Java 仓库提出代码问题。
2. Agent 能受限地列目录、搜索、读取文件和查看 Git Diff。
3. 最终答案包含可核查的文件与行号证据，并明确标注推断和未知项。
4. 全程没有仓库文件写入，也没有任意命令执行。
5. 越界路径、敏感文件、超大结果和超限循环均被确定性阻止。
6. 核心 Agent Loop 由脚本式 Fake Model 离线覆盖主要路径。
7. 至少覆盖直接回答、单工具、多工具、多 Tool Call、未知工具、非法参数、工具异常、模型异常、空响应和达到限制。
8. Windows 路径穿越及符号链接/Junction 逃逸测试通过。
9. 默认日志不包含 API Key、完整源码或完整 Prompt。
10. README 中的能力声明与实际实现一致。

## 14. M2 验收标准

1. 每个修复任务运行在独立 Worktree 和分支。
2. 原始工作区在任务前后保持不变。
3. 补丁只能作用于允许的文件和 Worktree 根路径。
4. 至少完成编译，并执行由变更范围选出的相关测试。
5. 失败、超时和取消都能生成可读报告。
6. 报告包含 Diff、命令模板、退出码、测试结果和风险说明。
7. Agent 不自动 commit、push、merge 或修改外部缺陷。
8. 人工明确选择后，补丁才进入后续处理。

## 15. 成功指标

### 15.1 工程指标

- 非授权文件访问次数：0。
- 非授权外部写操作次数：0。
- M1 核心 Loop 离线测试通过率：100%。
- 工具调用轨迹可解释率：100%。
- 因无限循环导致的未终止任务：0。

### 15.2 效果指标

在准备的历史缺陷或种子 Bug 集上统计：

- 调查报告能定位到相关文件的比例；
- 根因判断被人工认可的比例；
- M2 候选补丁编译通过率；
- 相关测试通过率；
- 补丁被人工接受的比例；
- 平均调查时长、模型轮次、Token 和费用；
- 因缺失信息进入 `NEEDS_INPUT` 的准确性。

在扩大自动化权限前，至少回放 20～30 个历史缺陷并保留结果。

## 16. 产品风险

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 仓库内容包含 Prompt Injection | 模型尝试绕过规则 | 权限策略由代码执行；仓库内容始终视为不可信数据 |
| 代码库含密钥或隐私数据 | 内容被发送给模型 | 敏感文件拒绝、结果截断、本地模型选项、默认关闭内容日志 |
| 模型错误调用工具 | 无效循环或误操作 | 工具白名单、Schema 校验、次数和时间限制 |
| 自动补丁看似合理但错误 | 引入回归 | Worktree、编译、测试、证据报告和人审 |
| 一开始范围过大 | 项目无法形成闭环 | M1 只读调查，按里程碑逐步授权 |
| 与现有商业产品同质化 | 开源价值不足 | 聚焦 Java/Spring、安全边界、评测和 FixBug 工作流 |

## 17. 待维护者确认

以下事项不会阻塞 M0 文档，但应在开始实现前确认：

1. Java 基线采用 17 还是 21；技术设计建议采用 Java 21。
2. 首个模型提供方与默认配置示例。
3. Maven GroupId 和 Java 根包名。
4. 开源许可证采用 Apache-2.0 还是 MIT。
5. CLI 采用普通 `main`、Picocli 还是其他方案；技术设计建议 Picocli。
6. M1 默认限制值，如最大轮次、工具次数、单文件大小和总耗时。
7. 项目名称 `cc-java` 是否作为长期公开名称。

## 18. 术语

- **Agent Loop**：模型请求工具、应用执行工具、结果返回模型，直到完成或终止的循环。
- **Tool**：由应用实现并授权给模型请求的确定性能力。
- **Worktree**：与当前开发工作区隔离的 Git 工作目录。
- **影子修复**：Agent 生成和验证补丁，但不自动进入共享分支。
- **证据报告**：包含事实、推断、工具轨迹、Diff 和验证结果的结构化输出。
- **MCP**：用于标准化连接外部工具与资源的协议；不是 M1 必需能力。
